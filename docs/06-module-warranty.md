# 06. Модуль 4 — `techdistrib_warranty`: ланцюжок доказів

> **Мета уроку:** побудувати бізнес-сутність, яка спирається на **уже наявні
> дані** Odoo (серійні номери, переміщення, замовлення) і перетворює їх
> на юридично достовірний доказ.
>
> **Закриває вимоги:** FR-D06, FR-E01 … FR-E08.

---

## 1. Бізнес-проблема, яку розв'язуємо

З бізнес-вимог (проблема **P3**):

> Гарантійні звернення велись у Google Sheets без прив'язки до серійного
> номера. Наслідок — неможливо довести вендору, що товар наш, і вендор
> відмовляє у компенсації. Збиток = повна вартість обладнання.

Розв'язок будується на одному принципі — **ланцюжок доказів**:

```
   серійний номер
        ↓  (ми його відвантажили?)
   відвантаження (stock.move.line, state='done')
        ↓  (за яким замовленням?)
   замовлення продажу (sale.order)
        ↓  (кому і коли?)
   клієнт + дата відвантаження
        ↓
   чи діє гарантія на дату звернення
```

Кожна ланка цього ланцюжка — це **факт у базі**, а не чиясь обіцянка.
Саме тому вендор приймає його як доказ.

## 3. Точка перехоплення: `_action_done` чи `button_validate`?

Найважливіше архітектурне рішення модуля.

```python
# ❌ Перехоплює лише натискання кнопки
def button_validate(self):
    ...

# ✅ Перехоплює САМУ ДІЮ
def _action_done(self):
    ...
```

`button_validate()` — це те, що натискає користувач: перевірки, візарди
backorder, підтвердження. `_action_done()` — те, що **реально виконує**
переміщення. Його викликає і `button_validate`, і код, і імпорт, і cron.

> **Правило:** перехоплюй **найглибший** метод, який виконує дію, а не той,
> який натискає користувач. Це той самий принцип, що в Модулі 2 з
> `action_confirm`.

### Коли що перед `super()` — критична деталь

У Модулі 2 ми перевіряли **до** `super()`:

```python
# Модуль 2: ЗАБОРОНА дії
def action_confirm(self):
    self._check_credit()      # якщо умову не виконано — дії не буде
    return super().action_confirm()
```

У Модулі 4 — **після**:

```python
# Модуль 4: ДОПОВНЕННЯ результату
def _action_done(self):
    result = super()._action_done()      # спершу виконуємо дію
    self._techdistrib_apply_warranty_dates()   # потім доповнюємо
    return result
```

**Чому різниця:** гарантію можна проставити лише тоді, коли переміщення
**вже завершено** (стан `done`, відомі номери й дата). До `super()` цих
даних просто немає.

> **Правило:**
> * **перевірки** — ДО `super()` (забороняємо дію);
> * **доповнення результату** — ПІСЛЯ `super()` (використовуємо результат).

## 4. Арифметика гарантії

```python
def _apply_warranty_dates(self, delivery_partner, sale_order, delivery_date):
    months = self._get_warranty_months()
    if months <= 0:
        return False
    self.write({
        'warranty_start_date': delivery_date,
        'warranty_end_date': delivery_date + relativedelta(months=months),
        'warranty_months_applied': months,
        ...
    })
```

### Чому `relativedelta`, а не `timedelta`

```python
from datetime import timedelta
from dateutil.relativedelta import relativedelta

date + timedelta(days=180)                 # ❌ «6 місяців» — це не 180 днів
date + relativedelta(months=6)             # ✅ правильно враховує місяці
```

Місяці мають різну кількість днів. Додати «36 місяців» через `timedelta`
неможливо в принципі — накопичиться похибка в тижні.

### Пастка: зміна терміну категорії

```python
warranty_months_applied = fields.Integer(readonly=True, copy=False)
```

Ми **зберігаємо** застосований термін окремо від поточного терміну категорії.
Причина: бізнес може змінити термін категорії (з 36 на 24 місяці), і тоді
для **уже проданих** одиниць гарантія не має перераховуватись — це було б
порушенням зобов'язань перед клієнтом.

### Що робити при повторній продажі

Якщо клієнт повернув товар і ми продали його знову — ми **перезаписуємо**
дати, бо гарантія для кінцевого клієнта йде від дати **його** покупки.

Але є нюанс: вендорська гарантія зазвичай іде від дати **виробництва** і
не перезапускається. Тому для звернень до вендора може знадобитись окреме
поле. Ми його **не робимо**: у BRD цього немає, а додавати поля «на всяк
випадок» — прямий шлях до роздутої моделі.

## 5. Модель звернення: знову знімок даних

```python
sale_order_id = fields.Many2one('sale.order', readonly=True, copy=False)
sold_to_partner_id = fields.Many2one('res.partner', readonly=True, copy=False)
delivery_date = fields.Date(readonly=True, copy=False)
```

Ці поля **зберігаються** на момент створення звернення — той самий принцип,
що в кредитних запитах (Модуль 2). Якщо через рік хтось змінить дані
серійного номера або замовлення, звернення має лишитись **юридично
достовірним документом**.

### Не додавай зайвих полів

```python
# ❌ Я так зробив спочатку
serial_number = fields.Char(related='lot_id.name', store=True)
```

Odoo попередив:

```
Two fields (serial_number, lot_id) of techdistrib.warranty.claim()
have the same label: Серійний номер
```

Причина: `display_name` серійного номера **вже є** його номером. Користувач
бачив би у формі два однакові поля під одним підписом — яке з них правити,
незрозуміло.

Для пошуку по номеру достатньо `[('lot_id.name', 'ilike', 'SN-123')]`.

> **Правило:** перед тим як додати related-поле, спитай себе —
> а чи не показує те саме значення вже наявне поле?

## 6. Перевірка гарантії: порівнюємо з датою ЗВЕРНЕННЯ

```python
check_date = self.reported_date or fields.Date.context_today(self)
if lot.warranty_end_date and lot.warranty_end_date >= check_date:
    ...  # гарантія дійсна
```

**Чому не `today`:** клієнт приніс обладнання 5 числа, документ оформлюють
10 числа. Якщо гарантія закінчилась 7 числа — прилад має вважатись
гарантійним, бо **на момент звернення** гарантія ще діяла.

Це не формальність: у сервісному відділі документи оформлюють із затримкою
в кілька днів, і без цієї деталі гарантійні прилади «на межі» перетворювались
би на платні ремонти.

На це є тест `test_warranty_checked_against_report_date_not_today`.

## 7. Пастка `@api.onchange`: працює лише в UI

```python
@api.onchange('lot_id')
def _onchange_lot_id(self):
    ...   # заповнити ланцюжок доказів
```

`onchange` викликається **лише у формі**. Імпорт з Excel, API, масове
створення, cron — усе це його **не викликає**.

Тому та сама логіка обов'язково дублюється в `create`:

```python
@api.model_create_multi
def create(self, vals_list):
    ...
    claims = super().create(vals_list)
    claims._fill_evidence_chain()      # ← працює ЗАВЖДИ
    return claims
```

На це є тест `test_claim_snapshots_dates_regardless_of_call_path`.

> **Правило:** `onchange` — для UX. Будь-яке поле, яке має бути заповнене
> завжди, заповнюй у `create`.

## 8. Третій раз та сама граблина: stored + non-stored в одному обчислювачі

```python
# ❌ Мій перший варіант
@api.depends(...)
def _compute_warranty_check(self):
    for claim in self:
        claim.is_our_product = ...        # store=True
        claim.is_under_warranty = ...     # store=True
        claim.is_chargeable = ...         # store=True
        claim.warranty_check_note = ...   # store=False  ← ось проблема
```

Odoo попередив:

```
UserWarning: techdistrib.warranty.claim: inconsistent 'store' for computed
fields, accessing warranty_check_note may recompute and update
is_our_product, is_under_warranty, is_chargeable.
```

**Це вже третій раз у проєкті** (Модуль 1 — метрики дилера, Модуль 4 — тут).
Тому варто запам'ятати твердо:

> **Один метод-обчислювач — один режим збереження для всіх його полів.**

### Правильне рішення: одна логіка — два обчислювачі

```python
def _evaluate_warranty(self):
    """Звичайний метод: повертає (is_our, is_under, is_chargeable, note)."""
    ...
    return (True, True, False, _('Гарантія діє до %s', ...))

@api.depends(...)
def _compute_warranty_check(self):
    """ЗБЕРЕЖЕНІ поля."""
    for claim in self:
        (claim.is_our_product,
         claim.is_under_warranty,
         claim.is_chargeable,
         _note) = claim._evaluate_warranty()

@api.depends(...)
def _compute_warranty_check_note(self):
    """НЕзбережене поле."""
    for claim in self:
        claim.warranty_check_note = claim._evaluate_warranty()[3]
```

Дублювання коду немає: обидва обчислювачі викликають спільний метод.
Це загальний патерн **«одна логіка — два обчислювачі»**.

Порада: винести логіку в звичайний метод корисно ще й тому, що її можна
викликати з тестів і з іншого коду, не торкаючись обчислювальних полів.

## 9. `is_overdue`: збережене поле + cron

```python
is_overdue = fields.Boolean(compute='_compute_deadline', store=True, index=True)
```

Це компроміс, і ось у чому:

* `is_overdue` потрібен у **фільтрах** («покажи прострочені»), а фільтрувати
  по незбереженому полю без `search=` не можна — Odoo мовчки проігнорує
  умову (див. [Модуль 2](04-module-credit.md), розділ 6);
* але збережене значення **«протухає»**: учора `False`, сьогодні мало б
  стати `True`, а ніщо не змінилось.

**Рішення — cron**, який щодня перераховує поле:

```python
@api.model
def _cron_refresh_overdue_claims(self):
    open_claims = self.search([('state', 'in', (...))])
    self.env.add_to_compute(self._fields['is_overdue'], open_claims)
```

Це той самий патерн «часової залежності», що в Модулі 1 зі статусом дилера.

### Порівняння трьох підходів до часових залежностей

| Підхід | Де застосовано | Плюс | Мінус |
|--------|----------------|------|-------|
| Не зберігати + `search=` | `credit_is_blocked` (Модуль 2) | Завжди актуально | Треба писати метод пошуку |
| Не зберігати, без фільтрів | `warranty_state` (Модуль 4) | Просто | Не можна фільтрувати |
| Зберігати + cron | `dealer_status`, `is_overdue` | Швидкий пошук і групування | Потрібен cron, є вікно неузгодженості |

Вибір залежить від того, чи потрібен **пошук** по цьому полю.

### Фільтр по даті — рецепт

Коли стан залежить від дати й потрібен фільтр, найпростіше — фільтрувати
по **збереженій даті**:

```xml
<filter name="filter_under_warranty" string="Гарантія дійсна"
        domain="[('warranty_end_date', '&gt;=', context_today().strftime('%Y-%m-%d'))]"/>
```

`context_today()` доступний у доменах подань і повертає **локальну** дату
користувача (не UTC) — саме те, що потрібно.

## 11. Головна пастка тестування: коли спрацьовує `@api.constrains`

```python
# ❌ Мій перший варіант — тест УПАВ
claim.resolution = 'reject'                # ← помилка вилітає ОСЬ ТУТ
with self.assertRaises(ValidationError):
    claim.action_resolve()                 # ← сюди не доходить
```

**Причина:** `@api.constrains` спрацьовує в момент **запису поля**, а не при
виклику бізнес-методу. `claim.resolution = 'reject'` — це вже write.

**Правильно:**

```python
with self.assertRaises(ValidationError):
    claim.resolution = 'reject'

# Записуємо обидва поля ОДНІЄЮ операцією — тоді constrains бачить
# заповнене обґрунтування і не піднімає помилку
claim.write({
    'resolution': 'reject',
    'resolution_note': 'Механічне пошкодження не є гарантійним випадком.',
})
claim.action_resolve()
```

> **Урок:** `@api.constrains` захищає від **будь-якого** способу запису —
> форма, імпорт, API. Саме тому вона спрацьовує так рано. У тесті це треба
> враховувати: помилка може вилетіти **раніше**, ніж ти очікуєш.

## 12. Зміна моделі товарів в Odoo 18: `is_storable`

П'ять тестів упали з:

```
ValidationError: Quants cannot be created for consumables or services.
```

Причина — зміна моделі товарів. У Odoo ≤17 було три **типи**:

| Було (≤17) | Значення |
|------------|----------|
| `type='product'` | Товар зі складським обліком |
| `type='consu'` | Витратний матеріал (без обліку) |
| `type='service'` | Послуга |

У Odoo 18 типів теж три, але **інших**:

| Стало (18) | Значення |
|------------|----------|
| `type='consu'` | «Goods» — усі матеріальні товари |
| `type='service'` | Послуга |
| `type='combo'` | Набір |

А чи ведеться складський облік — визначає **окремий прапорець**
`is_storable`, який додає модуль `stock`:

```python
# addons/stock/models/product.py:704
is_storable = fields.Boolean(...)
```

**Правильно для Odoo 18:**

```python
{'type': 'consu', 'is_storable': True}
```

> **Це найнебезпечніший різновид застарілого знання:** код виглядає звично,
> компілюється, не дає помилок при створенні — і падає лише тоді, коли
> спрацьовує перевірка на складі.
>
> **Рецепт перевірки:** коли щось «не працює як раніше», подивись оголошення
> поля в ядрі:
> ```bash
> grep -rn "is_storable = fields" vendor/odoo/addons/stock/
> ```

## 13. Помилки цього уроку

| # | Помилка | Симптом | Урок |
|---|---------|---------|------|
| 1 | Дія оголошена після подання | `External ID not found` | Порядок: дії → подання → меню (**вже друга така помилка в проєкті**) |
| 2 | `serial_number` дублював `lot_id` | `Two fields have the same label` | Не додавай related-поле, якщо значення вже показується |
| 3 | stored + non-stored в одному обчислювачі | `inconsistent 'store'` | **Третій раз у проєкті.** Один обчислювач — один режим |
| 4 | `type='consu'` без `is_storable` | `Quants cannot be created for consumables` | Модель товарів змінилась у Odoo 18 |
| 5 | Номер без гарантії → `action_confirm` | `UserError: Неможливо прийняти` | Бізнес-перевірка спрацювала правильно — помилка була в тесті |
| 6 | `assertRaises` навколо `action_resolve` | Помилка вилетіла поза блоком | `@api.constrains` спрацьовує на **записі поля**, а не на виклику методу |

Зверни увагу на помилку №5: **тест упав, а код був правий.** Це нормальна
ситуація. Коли тест падає, перше питання — не «що зламати в коді», а
«а чи правильно тест формулює очікування».

2. Підтвердити → перейти до відвантаження → вказати серійний номер →
   **Підтвердити**.
3. Відкрити **Склад → Серійні номери** → знайти номер → вкладка **Гарантія**:
   дати проставлені автоматично.
4. Натиснути **Гарантійне звернення** → створиться RMA з ланцюжком доказів.
5. У формі звернення — зелений банер «Товар наш. Гарантія діє до ...».

## 15. Чек-ліст

- [ ] Спершу перевірено, чого немає в Odoo (`grep` по `addons/`)
- [ ] Перехоплено **найглибший** метод дії, а не кнопку UI
- [ ] Перевірки — до `super()`, доповнення результату — після
- [ ] Дати рахуються через `relativedelta`, не `timedelta`
- [ ] Логіка є **і** в `onchange`, **і** в `create`
- [ ] Обчислювачі не змішують `store=True` і `store=False`
- [ ] Збережені поля-знімки мають `copy=False`
- [ ] Фільтри по часових станах — по **збереженій даті** або через `search=`
- [ ] Cron ідемпотентний (нагадування не дублюються)
- [ ] `./scripts/run_tests.sh techdistrib_warranty` — усе зелене

## 16. Вправи

1. **Легка.** Додай у звернення поле «Спосіб доставки в сервіс» (кур'єр /
   дилер привіз / клієнт приніс) і виведи його в канбані.

2. **Середня.** Зроби друковану форму **гарантійного талона** (QWeb PDF)
   з серійним номером, датами продажу й гарантії, назвою товару.

3. **Середня.** Додай звіт «Відкриті гарантійні звернення» з групуванням
   по відповідальному і підсвіткою прострочених.

4. **Складна.** Реалізуй **автоматичне створення зворотного переміщення**
   (повернення обладнання з сервісу клієнту) при закритті звернення
   з рішенням «ремонт». Підказка: `stock.picking` типу `incoming` +
   `stock.picking` типу `outgoing`.

5. **Складна.** Додай звіт для вендора: список серійних номерів із датами
   продажу й описами несправностей — як обґрунтування компенсації.
   Це та сама вимога FR-E08, яка в BRD прямо пов'язана з проблемою P3.
