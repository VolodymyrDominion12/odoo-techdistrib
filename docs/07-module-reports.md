## 1. Головний урок: 80 % звітів — це не код

Коли бізнес каже «нам потрібен звіт», перше питання має бути не
«як це запрограмувати», а **«чи вистачить аналітичного подання?»**.

В Odoo є два типи подань, які дають готовий звіт **без жодного рядка Python**:

| Подання | Що це | Аналог |
|---------|-------|--------|
| `<graph>` | Діаграма (стовпчики, лінії, коло) | — |
| `<pivot>` | Зведена таблиця | Excel-зведені |

Ось повний код звіту «Скільки грошей ми віддали на перевищеннях ліміту»:

```xml
<record id="view_credit_request_pivot" model="ir.ui.view">
    <field name="name">techdistrib.credit.request.pivot</field>
    <field name="model">techdistrib.credit.request</field>
    <field name="arch" type="xml">
        <pivot string="Кредитні перевищення">
            <field name="partner_id" type="row"/>
            <field name="state" type="col"/>
            <field name="create_date" interval="month" type="col"/>
            <field name="order_amount" type="measure"/>
            <field name="excess_amount" type="measure"/>
        </pivot>
    </field>
</record>
```

І все. Користувач отримує:

* групування по будь-якому виміру (перетягуванням мишею);
* розгортання/згортання рівнів;
* експорт у **XLSX** і **PDF** (кнопка є автоматично);
* збереження власних конфігурацій звіту;
* фільтри й пошук.

Якби ми писали це кодом, довелося б робити SQL-агрегації, будувати форму
фільтрів, реалізовувати експорт... і все це підтримувати.

### `type="measure"` — не косметика

```xml
<field name="excess_amount" type="measure"/>
```

Без цього Odoo підсумує **усі** числові поля моделі підряд, і таблиця
стане нечитабельною. `type="measure"` явно позначає показники.

Аналогічно `type="row"` і `type="col"` явно задають виміри.

> **Правило:** перш ніж писати звіт — спитай, чи вистачить `graph`/`pivot`.
> Код пиши лише коли потрібен **друкований документ** або складна
> бізнес-логіка агрегації.

## 2. QWeb PDF: як працює друк в Odoo

Друк — це конвеєр із трьох ланок:

```
   1. Шаблон QWeb          XML із тегами t-if, t-foreach, t-field → HTML
          ↓
   2. Запис ir.actions.report   «для моделі X друкуй шаблон Y»
          ↓
   3. wkhtmltopdf          конвертує HTML → PDF (зовнішня програма!)
```

### Шаблон: три рівні вкладеності, усі обов'язкові

```xml
<template id="report_warranty_certificate_document">
    <t t-call="web.html_container">          <!-- 1. HTML-обгортка -->
        <t t-foreach="docs" t-as="o">        <!-- 2. цикл по документах -->
            <t t-call="web.external_layout"> <!-- 3. шапка й підвал компанії -->
                <div class="page">           <!-- 4. ВМІСТ (клас обов'язковий!) -->
                    ...
                </div>
            </t>
        </t>
    </t>
</template>
```

* `t-foreach="docs"` — `docs` це recordset документів. Дає змогу надрукувати
  кілька звернень одразу, виділивши їх у списку.
* `web.external_layout` — готовий блок із логотипом, адресою компанії,
  нумерацією сторінок. Не малюй шапку вручну.
* `class="page"` — **критичний**. Саме він позначає межі сторінки для
  wkhtmltopdf. Без нього документ стиснеться в одну довгу смугу.

### Дія друку

```xml
<record id="action_report_warranty_certificate" model="ir.actions.report">
    <field name="name">Гарантійний талон</field>
    <field name="model">techdistrib.warranty.claim</field>
    <field name="report_type">qweb-pdf</field>
    <field name="report_name">techdistrib_reports.report_warranty_certificate_document</field>
    <field name="print_report_name">'Гарантійний талон - %s' % (object.name)</field>
    <field name="binding_model_id" ref="techdistrib_warranty.model_techdistrib_warranty_claim"/>
    <field name="binding_type">report</field>
</record>
```

`binding_model_id` + `binding_type` додають пункт **«Гарантійний талон»**
у меню «Друк» на формі та в списку. Без них звіт існує, але дістатись до
нього можна лише через Technical-меню.

### Принцип «одне джерело істини» в шаблоні

У шаблоні ми **не** пишемо логіку «дійсна/не дійсна гарантія»:

```xml
<!-- ✅ Виводимо готовий рядок із моделі -->
<span t-field="o.warranty_check_note"/>
```

Поле `warranty_check_note` уже містить і дату закінчення, і кількість днів.
Якби ми дублювали цю логіку в шаблоні, то при зміні правил довелося б
правити і код, і шаблон — і колись їх забули б синхронізувати.

## 3. Проблема wkhtmltopdf і рішення без root

**Без `wkhtmltopdf` друк PDF не працює взагалі.** Odoo пише в лог:

```
You need Wkhtmltopdf to print a pdf version of the reports.
```

У нашому середовищі немає `sudo`, тому `apt install wkhtmltopdf` неможливий.
Але є обхід: **портативна збірка з `.deb`, розпакована без прав root**.

```bash
# 1. Завантажуємо .deb з офіційного релізу
curl -sSL -o wk.deb \
  "https://github.com/wkhtmltopdf/packaging/releases/download/0.12.6.1-3/wkhtmltox_0.12.6.1-3.jammy_amd64.deb"

# 2. Розпаковуємо БЕЗ root — dpkg-deb -x не потребує прав адміністратора
dpkg-deb -x wk.deb extracted

# 3. Бінарник тут:
#    extracted/usr/local/bin/wkhtmltopdf
```

Odoo шукає бінарник простим пошуком у PATH
(`odoo/addons/base/models/ir_actions_report.py:62`, `find_in_path('wkhtmltopdf')`).
Тому достатньо додати теку в PATH перед запуском:

```bash
export PATH="$ROOT/vendor/wkhtmltopdf/extracted/usr/local/bin:$PATH"
```

Це вже зроблено в `scripts/run_odoo.sh` і `scripts/run_tests.sh`.

> **Урок:** обмеження середовища не завжди означає «функція недоступна».
> `.deb` — це архів; його можна розпакувати куди завгодно. Те саме
> стосується багатьох системних залежностей.

## 4. Ретро-бонуси: агрегація ЧУЖИХ даних

FR-F04/F05: «бонус = % від обороту за квартал, розрахунок автоматично
після закриття періоду».

Це третій тип нової бізнес-сутності в проєкті (після кредитного запиту
й гарантійного звернення), і він демонструє **новий тип роботи з даними**:
не власний життєвий цикл операції, а **агрегація даних іншої моделі**.

```python
def _get_period_purchase_orders(self):
    self.ensure_one()
    return self.env['purchase.order'].search([
        ('partner_id', '=', self.vendor_id.id),
        ('company_id', '=', self.company_id.id),
        ('state', 'in', ('purchase', 'done')),
        ('date_order', '>=', self.date_from),
        ('date_order', '<=', self.date_to),
    ])
```

### `@api.depends` не може бути повним — і це нормально

```python
@api.depends('vendor_id', 'date_from', 'date_to', 'company_id', 'rebate_percent')
def _compute_rebate_amount(self):
```

Ми **не можемо** вказати залежність від `purchase.order.date_order`:
між моделями немає прямого зв'язку (Many2one), по якому Odoo побудував би
граф залежностей.

**Наслідок:** поле не оновиться саме собою, коли в періоді з'явиться нова
закупівля. Потрібен явний механізм:

```python
def action_recalculate(self):
    """Кнопка «Перерахувати»."""
    self.env.add_to_compute(self._fields['purchase_amount'], self)
```

Плюс cron перераховує **чернетки**.

Це той самий патерн «рятівної кнопки», що в матриці знижок: коли значення
залежить від даних, які Odoo не бачить через граф залежностей, людині
потрібен спосіб сказати «порахуй зараз».

### Чому суми зберігаються, а не рахуються на льоту

```python
purchase_amount = fields.Monetary(compute='...', store=True)
```

Причина та сама, що в кредитних запитах: **нарахування за закритий квартал
має лишитись незмінним документом**. Якщо через рік хтось виправить суму
в закупівлі минулого кварталу, бонус уже виплачено, і перераховувати його
не можна.

Саме тому `action_confirm()` робить документ незмінним, а cron перераховує
**лише чернетки**.

### База розрахунку — сума без ПДВ

```python
rebate.purchase_amount = sum(orders.mapped('amount_untaxed'))
```

Той самий урок, що в Модулі 1: ПДВ не є ні нашими витратами, ні оборотом,
від якого вендор платить бонус.

## 5. Арифметика кварталів: помилка «на один день»

Найризикованіша частина модуля. Розберемо алгоритм:

```python
quarter_start_month = ((reference_date.month - 1) // 3) * 3 + 1
current_quarter_start = date(reference_date.year, quarter_start_month, 1)
previous_quarter_end = current_quarter_start - timedelta(days=1)
previous_quarter_start = previous_quarter_end.replace(day=1) - relativedelta(months=2)
```

Перевіримо на прикладі `2026-05-15`:

| Крок | Обчислення | Результат |
|------|-----------|-----------|
| 1 | `((5-1)//3)*3+1 = (4//3)*3+1 = 1*3+1` | квітень (4) |
| 2 | початок поточного кварталу | `2026-04-01` |
| 3 | мінус 1 день | `2026-03-31` |
| 4 | `2026-03-01` мінус 2 місяці | `2026-01-01` |

→ Q1 2026: `01.01 — 31.03` ✓

**Чому це небезпечно:** помилка «на один день» непомітна в інтерфейсі,
але призводить до того, що закупівля від 31 березня випадає з бонусу —
або потрапляє двічі (і в Q1, і в Q2).

Тому на арифметику кварталів є **чотири** тести, включно з межами:

```python
def test_previous_quarter_first_day_of_quarter(self):
    """1 квітня → попередній квартал теж Q1. Це найнебезпечніший день: межа."""
    date_from, date_to = self.rebate_model._get_previous_quarter_dates(date(2026, 4, 1))
    self.assertEqual(date_from, date(2026, 1, 1))
    self.assertEqual(date_to, date(2026, 3, 31))

def test_previous_quarter_year_boundary(self):
    """Лютий 2027 → Q4 2026 (перехід через рік)."""
```

І окремий тест на межі періоду в самих даних:

```python
def test_orders_outside_period_not_counted(self):
    self._create_purchase(self.vendor, 100000.0, '2026-03-31 23:00:00')  # Q1 ✓
    self._create_purchase(self.vendor, 500000.0, '2026-04-01 00:30:00')  # Q2 ✗
```

> **Урок:** будь-яка робота з датами потребує тестів на **межах**:
> перший день, останній день, перехід через рік, перехід через місяць.

## 6. Cron: самолікування розкладу

```xml
<field name="interval_type">days</field>
<field name="interval_number">1</field>
```

Задача запускається **щодня**, але створює нарахування лише тоді, коли
їх ще немає.

**Чому не «раз на квартал у конкретну дату»:** якщо сервер того дня лежав,
нарахування не створиться **зовсім**. А щоденна ідемпотентна перевірка
«наздожене» пропущене.

> **Принцип самолікування розкладу:** періодична задача має доганяти
> пропущене, а не втрачати його назавжди.

### Два рубежі ідемпотентності

```python
existing = self.search([('vendor_id', '=', vendor.id),
                        ('date_from', '=', date_from), ...], limit=1)
if existing:
    continue        # ← перший рубіж: явна перевірка

self.create({...})  # ← другий рубіж: SQL-обмеження unique(...)
```

* **явна перевірка** — чиста робота без помилок у логах;
* **SQL-обмеження** — спрацює навіть при одночасному запуску двох воркерів,
  де перевірка могла б пропустити дубль.

Потрібні **обидва**. Це той самий принцип, що в Модулі 1 з кодами дилерів.

## 7. Четвертий раз та сама граблина (і чому це важливо)

У цьому модулі я знову написав **один** обчислювач, який присвоював і
збережені поля, і незбережене:

```python
# ❌ ЧЕТВЕРТИЙ РАЗ У ПРОЄКТІ
@api.depends(...)
def _compute_rebate_amount(self):
    rebate.purchase_amount = ...        # store=True
    rebate.rebate_amount = ...          # store=True
    rebate.purchase_order_count = ...   # store=False  ← ось проблема
```

Odoo попередив:

```
UserWarning: techdistrib.vendor.rebate: inconsistent 'store' for computed
fields, accessing purchase_order_count may recompute and update
purchase_amount, rebate_amount.
```

### Історія цієї помилки в проєкті

| # | Модуль | Поля |
|---|--------|------|
| 1 | `techdistrib_base` | метрики дилера |
| 2 | `techdistrib_warranty` | перевірка гарантії |
| 3 | `techdistrib_reports` | підсумки бонусу |

**Чому це легко зробити:** обчислювач логічно «про одне» — «порахувати
підсумки за період». Природно покласти в нього **усі** підсумки. А про те,
що в частини полів `store=True`, а в частини ні, згадуєш аж коли Odoo
попередить.

**Чому це небезпечно:** незбережене поле рахується при **кожному** читанні,
а метод заразом перезаписує збережені. Виникають несподівані `UPDATE`
в базі під час звичайного перегляду списку.

### Правило

> **ОДИН МЕТОД-ОБЧИСЛЮВАЧ = ОДИН РЕЖИМ ЗБЕРЕЖЕННЯ.**

Спільну логіку винось у звичайний метод:

```python
def _get_period_purchase_orders(self):     # спільна логіка
    ...

@api.depends(...)
def _compute_rebate_amount(self):          # ЗБЕРЕЖЕНІ поля
    ...

@api.depends(...)
def _compute_purchase_order_count(self):   # НЕзбережене поле
    ...
```

## 13. Куди рухатись далі

Проєкт завершено, але Odoo великий. Напрямки для подальшого вивчення:

| Напрямок | Що вивчати |
|----------|-----------|
| **Портал** | `portal` — самообслуговування дилерів |
| **Веб-клієнт** | OWL-компоненти, власні віджети |
| **Інтеграції** | REST/XML-RPC, `base_automation` |
| **Мультикомпанійність** | `company_dependent` поля, правила компаній |
| **Локалізація** | `l10n_ua` — український план рахунків і звітність |
| **Продуктивність** | `read_group`, `_read_group`, індекси, `prefetch` |
| **Тестування** | `HttpCase` — тести веб-маршрутів і UI |

задачі, які ти щойно розв'язував своїми руками.
