## 3. Модель запиту: чому окрема сутність

Виникає спокуса зробити «прапорець на замовленні»: `credit_approved = True`.
Але BRD вимагає (NFR-04):

* хто попросив, коли і чому;
* хто схвалив, коли і на підставі чого;
* можливість відхилити з причиною;
* чергу запитів, що чекають рішення;
* строк дії схвалення.

**Ознака, коли потрібна власна модель:** у процесу є власний життєвий цикл
(стани) і власні атрибути (хто, коли, чому). Прапорець цього не вміє.

### Знімок сум — важливе архітектурне рішення

```python
credit_limit = fields.Monetary(...)   # знімок на момент запиту
current_debt = fields.Monetary(...)   # знімок
order_amount = fields.Monetary(...)   # знімок
```

Ми **зберігаємо** суми, а не перераховуємо щоразу. Чому: якщо через місяць
контролер відкриє старий запит, він має побачити **ті самі цифри**, на підставі
яких ухвалював рішення. Інакше аудит безглуздий — суми «пливуть» разом із
поточним боргом дилера.

Це загальний принцип для будь-якого документ-процесу: **знімок стану на момент
рішення зберігається окремо від поточного стану сутності.**

## 4. Блокування: чому в методі, а не в кнопці

```python
def action_confirm(self):
    blocked = self.before_after_confirm_filter()
    if blocked:
        raise UserError(...)
    return super().action_confirm()
```

`action_confirm()` викликається **звідусіль**: кнопка на формі, масове
підтвердження зі списку, API, імпорт, інший код. Перевизначивши **метод**,
ми контролюємо всі ці шляхи.

Якби перевірка стояла в окремій кнопці, ліміт обходився б масовим
підтвердженням. На це є тест:

```python
def test_blocking_is_not_bypassable_via_mass_confirm(self):
    orders = allowed | blocked
    with self.assertRaises(UserError):
        orders.action_confirm()
```

> **Правило:** контроль бізнес-правила ставиться в **метод**, а не в UI.
> UI — лише один зі способів викликати метод.

### Перевірка — ПЕРШОЮ, дія — ПОТІМ

Ми кидаємо помилку **до** `super()`. Це принципово:

`action_confirm()` робить багато: змінює стан, створює відвантаження,
резервує товар. Усе це — одна транзакція Postgres. Якби ми перевіряли
**після** `super()`, а потім кидали помилку, Odoo відкотив би транзакцію —
але користувач побачив би помилку після «успішного» підтвердження, а частина
побічних ефектів (email, повідомлення в cron) могла б виконатись у суміжних
транзакціях і **не відкотитися**.

## 5. Пастка, яка зламала б усе: `UserError` відкочує транзакцію

Найковарніша помилка цього модуля. Розглянемо спокусливий код:

```python
def action_confirm(self):
    if self._over_limit():
        # ❌ ТАК РОБИТИ НЕ МОЖНА
        self.env['techdistrib.credit.request'].create({...})   # створили запит
        raise UserError('Перевищено ліміт!')                   # ...і одразу відкотили
```

**Що станеться:** `UserError` → Odoo відкочує **всю транзакцію** → щойно
створений запит **зникає**. Користувач бачить помилку, а запиту немає.
Класична пастка «дані зникають після помилки».

**Правильне рішення:** створення запиту — **окрема дія**, яку користувач
запускає явно кнопкою `action_request_credit_approval()`. Вона завершується
успішно, транзакція фіксується, запит живе.

> **Загальне правило:** якщо в середині обробки помилки треба щось ЗБЕРЕГТИ —
> це має бути окрема транзакція або окрема дія. Інакше відкат знищить твій запис.

## 6. Найголовніша пастка: незбережені поля не можна шукати

Це відкриття варте окремого розділу, бо воно **тихе**.

У нас є обчислюване поле, яке не зберігається:

```python
credit_is_blocked = fields.Boolean(compute='_compute_credit_overdue', compute_sudo=True)
```

І фільтр у пошуку:

```xml
<filter name="filter_credit_overdue" string="Заблоковані за борг"
        domain="[('credit_is_blocked', '=', True)]"/>
```

Логічно припустити, що Odoo видасть помилку «поле не підтримує пошук».
**Він не видає.** Ось код ядра (`vendor/odoo/odoo/osv/expression.py:1179`):

```python
elif not field.store:
    # Non-stored field should provide an implementation of search.
    if not field.search:
        # field does not support search!
        _logger.error("Non-stored field %s cannot be searched.", field, exc_info=True)
        # Ignore it: generate a dummy leaf.
        domain = []
```

Odoo пише ERROR **у лог** і повертає **порожній домен** — тобто **мовчки
ігнорує умову фільтра**. Фільтр «показати заблокованих» показав би **усіх**
партнерів. Користувач бачить неправильні дані й не здогадується про проблему.

**Це гірше за явну помилку.** Явна помилка змушує полагодити. Тиха —
породжує хибні рішення.

### Рішення: реалізувати метод пошуку

```python
credit_is_blocked = fields.Boolean(
    compute='_compute_credit_overdue',
    search='_search_credit_is_blocked',      # ← обов'язково!
)

@api.model
def _search_credit_is_blocked(self, operator, value):
    """Перекласти 'credit_is_blocked = True' у домен по рахунках."""
    if operator not in ('=', '!='):
        raise UserError(_('Підтримуються лише оператори = та !='))
    want_blocked = (operator == '=' and value) or (operator == '!=' and not value)
    overdue_invoices = self.env['account.move'].search([...])
    blocked = overdue_invoices.mapped('commercial_partner_id')
    ...
    return [('id', 'in', blocked.ids)]
```

Метод пошуку отримує `(operator, value)` і повертає **звичайний домен**,
який виражає ту саму умову через **збережені** поля. Ми не рахуємо нічого
самі — ми перекладаємо умову на рахунки, бо саме вони джерело істини.

І на це є тести — вони захищають саме від тихого ігнорування:

```python
def test_search_blocked_partners_returns_only_blocked(self):
    found = self.env['res.partner'].search([('credit_is_blocked', '=', True), ...])
    self.assertNotIn(clean, found,
        'Якщо цей тест упав — ймовірно, поле втратило search=')
```

> **Запам'ятай:** фільтруєш по computed-полю → перевір, чи воно `store=True`.
> Якщо ні — тобі потрібен `search=`.

## 7. Пастка валют

`res.partner.credit` — у **валюті компанії** (з бухгалтерських проводок).
`sale.order.amount_total` — у **валюті замовлення** (може бути USD чи EUR).

```python
# ❌ Порівняння доларів з гривнями
if partner.credit + order.amount_total > partner.credit_limit:

# ✅ Конвертація у валюту компанії
amount_company_currency = order.amount_total / order.currency_rate
```

Odoo робить саме так (`sale/models/sale_order.py:780`):

```python
current_amount=(order.amount_total / order.currency_rate),
```

Для дистриб'ютора з імпортом більшість замовлень валютні — без конвертації
ліміт «працював» би неправильно майже завжди.

## 8. Групи доступу на полях ламають логіку

Стандартні поля оголошені так:

```python
credit = fields.Monetary(..., groups='account.group_account_invoice,account.group_account_readonly')
credit_limit = fields.Float(..., groups='account.group_account_invoice,account.group_account_readonly')
```

Атрибут `groups=` — це **справжня перевірка в ORM**, а не приховування в UI.
Звичайний менеджер із продажу **не може прочитати** `credit_limit`.

**Наслідок:** наша перевірка ліміту, запущена від імені менеджера, впаде
з `AccessError`. А якщо «полагодити» це через `try/except` — менеджер без
бухгалтерських груп **обходив би кредитний ліміт**, бо перевірка не змогла б
його прочитати.

**Правильне рішення** — те саме, що використовує сам Odoo
(`sale/models/sale_order.py:783`):

```python
order.sudo()  # ensure access to `credit` & `credit_limit` fields
```

У нас це реалізовано через `compute_sudo=True` на полях і явний `.sudo()`
у методі перевірки.

> **Урок:** `groups=` на полі — це не косметика. Воно може зробити твою
> бізнес-логіку неробочою або, гірше, непомітно дірявою.

## 9. Права доступу: два рубежі + пастка OR

### Рубежі

| Рубіж | Файл | Гранулярність |
|-------|------|---------------|
| 1. Модельні права | `ir.model.access.csv` | «чи можна чіпати таблицю» |
| 2. Правила записів | `ir.rule` | «які рядки видно» |
| 3. Бізнес-перевірка | Python | «що саме дозволено робити» |

Третій рубіж обов'язковий, бо ACL грубі: вони кажуть «можна писати в модель»,
а не «можна змінювати **стан**». Менеджер **має** створювати запити — але не
схвалювати їх.

### Пастка OR у правилах Odoo

Мета: менеджер бачить лише свої запити, контролер — усі.

```xml
<!-- ❌ НЕПРАВИЛЬНО: одне обмежувальне правило -->
<record id="rule_credit_request_own" model="ir.rule">
    <field name="domain_force">[('requested_by', '=', user.id)]</field>
    <field name="groups" eval="[(4, ref('techdistrib_base.group_dealer_user'))]"/>
</record>
```

Чому не працює: контролер **теж** входить у `group_dealer_user` (через
`implied_ids`). Він потрапить під обмеження й побачить лише свої запити.
Привілейована роль виявиться обмеженою.

**Правильний патерн — ДВА правила:**

```xml
<!-- обмежувальне для менеджерів -->
<record id="rule_credit_request_own" model="ir.rule">
    <field name="domain_force">[('requested_by', '=', user.id)]</field>
    <field name="groups" eval="[(4, ref('techdistrib_base.group_dealer_user'))]"/>
    <field name="perm_read" eval="True"/>  <!-- для ВСІХ операцій! -->
    ...
</record>

<!-- дозвільне для контролера: [(1,'=',1)] — ідіома «завжди істина» -->
<record id="rule_credit_request_controller_all" model="ir.rule">
    <field name="domain_force">[(1, '=', 1)]</field>
    <field name="groups" eval="[(4, ref('group_credit_controller'))]"/>
    ...
</record>
```

**Як Odoo об'єднує правила:**
* глобальні (без `groups`) — через **AND** (лише звужують);
* правила груп — через **OR** між собою.

Тому дозвільне правило «розчиняє» обмеження для контролера.

Ще одна деталь: якщо поставити `perm_write="False"` на обмежувальному правилі,
воно **не застосовуватиметься** до запису — і менеджер зміг би редагувати чужі
запити, хоча не бачив би їх у списку. Тому у нас `True` для всіх операцій.

## 10. Ще одна помилка порядку: посилання на дію до її оголошення

```
ValueError: External ID not found in the system:
            techdistrib_credit.action_credit_request_from_order
ParseError: while parsing .../views/credit_request_views.xml:96
```

Я використав у формі кнопку, що посилається на дію:

```xml
<button name="%(action_credit_request_from_order)d" type="action"/>
```

…а сама дія була оголошена **нижче** в тому ж файлі. Odoo читає data-файли
**строго згори вниз** і резолвить `%(xml_id)d` **одразу**.

**Правило порядку всередині файлу:**
1. дії (`ir.actions.*`)
2. подання (`ir.ui.view`) — бо посилаються на дії
3. меню (`menuitem`) — бо посилаються на дії

Те саме стосується груп, послідовностей і будь-яких інших записів.

## 12. Чек-ліст «модуль готовий»

- [ ] Перш ніж оголошувати поле — перевірено, чи його немає в Odoo
- [ ] Контроль стоїть у **методі**, а не в кнопці UI
- [ ] Перевірка виконується **до** `super()`
- [ ] Все, що треба зберегти, не створюється в транзакції, яку потім відкочують
- [ ] Для **кожного** незбереженого поля, по якому є фільтр, реалізовано `search=`
- [ ] Суми різних валют конвертуються перед порівнянням
- [ ] Поля з `groups=` читаються через `sudo()`, якщо логіка має працювати для всіх
- [ ] Правила `ir.rule` для привілейованої групи мають **дозвільне** правило
- [ ] У data-файлі дії оголошені **перед** поданнями
- [ ] `./scripts/run_tests.sh techdistrib_credit` — усе зелене
- [ ] При оновленні модуля **немає WARNING-ів** у логах

   компанії (або `res.config.settings`), щоб адміністратор міг змінювати
   строк дії схвалення з інтерфейсу, а не через системний параметр.

2. **Середня.** Додай «м'яке» попередження: якщо перевищення менше ніж 5 %
   від ліміту — не блокувати, а лише показувати банер. Подумай, де має жити
   цей відсоток (константа? поле компанії?).

3. **Середня.** Зроби так, щоб при схваленні запиту менеджеру дилера
   надсилалось повідомлення (`mail.activity` або `message_post`
   на партнера).

4. **Складна.** Реалізуй `_search_credit_used` так, щоб можна було фільтрувати
   партнерів за «використано ліміту > X». Порівняй два підходи:
   через `search=` і через `store=True` + cron. Який краще і чому?

5. **Складна.** Додай у запит поле «бажана дата відвантаження» і логіку:
   якщо схвалення прострочене, а відвантаження вже частково виконане —
   не блокувати повторно, а створити задачу контролеру.
