## 1. Що таке Odoo в одному абзаці

Odoo — це **модульний моноліт**: один Python-процес, який містить і ORM, і
веб-сервер, і бізнес-логіку, а всі дані зберігає в одній базі PostgreSQL.
«Модульний» означає, що функціональність зібрана з незалежних модулів
(продажі, склад, бухгалтерія), які можна вмикати й вимикати. «Моноліт» —
що всі вони працюють в одному процесі й одній базі, тому **будь-який модуль
може звертатись до даних будь-якого іншого**.

Це ключова відмінність від мікросервісної архітектури: тут немає API між
«модулем складу» і «модулем продажів» — вони просто бачать одні й ті самі
об'єкти в пам'яті.

```
                    ┌──────────────────────────────────────┐
   Браузер  ◄──────►│  Веб-сервер (Werkzeug)               │
                    │    └── Controllers  (@http.route)    │
                    └───────────────┬──────────────────────┘
                                    │  викликає методи моделей
                    ┌───────────────▼──────────────────────┐
                    │  ORM (Object-Relational Mapping)     │
                    │    └── Models: res.partner,          │
                    │        sale.order, stock.lot ...     │
                    └───────────────┬──────────────────────┘
                                    │  генерує SQL
                    ┌───────────────▼──────────────────────┐
                    │  PostgreSQL                          │
                    │    └── таблиці: res_partner,         │
                    │        sale_order, stock_lot ...     │
                    └──────────────────────────────────────┘
```

**Три шари, які треба розрізняти:**

| Шар | Що це | Де живе |
|-----|-------|---------|
| **Модель** | Python-клас з логікою і полями | `models/*.py` |
| **Таблиця** | Фізична таблиця в Postgres | створюється ORM автоматично |
| **Подання (view)** | Опис того, як модель виглядає в UI | `views/*.xml` |

> **Помилка №1 новачків:** плутати модель і таблицю. Ти ніколи не пишеш
> `CREATE TABLE` і не пишеш `SELECT`. Ти описуєш клас — ORM сам створить
> таблицю, додасть колонки, індекси та зовнішні ключі.

## 2. Що таке модуль (addon)

Модуль — це звичайна директорія з обов'язковим файлом `__manifest__.py`.
Мінімальний модуль виглядає так:

```
techdistrib_base/
├── __manifest__.py       ← «паспорт» модуля: назва, залежності, перелік файлів
├── __init__.py           ← точка входу Python; імпортує підпакети
├── models/
│   ├── __init__.py
│   └── res_partner.py
├── views/
│   └── res_partner_views.xml
├── security/
│   └── ir.model.access.csv
└── tests/
    └── test_dealer.py
```

### `__manifest__.py` — паспорт модуля

```python
{
    'name': 'TechDistrib: Base',        # назва, яку побачить користувач
    'version': '18.0.1.0.0',            # ВАЖЛИВО: перші дві цифри = версія Odoo
    'depends': ['base', 'contacts'],    # від чого залежимо — вантажиться першим
    'data': [                           # файли, які Odoo прочитає при встановленні
        'security/ir.model.access.csv',
        'views/res_partner_views.xml',
    ],
    'installable': True,
    'application': False,               # True = показувати як окремий застосунок
    'license': 'LGPL-3',
}
```

**Порядок у `depends` і в `data` має значення.** `depends` гарантує, що
залежні модулі встановляться раніше. `data` читається зверху вниз: якщо view
посилається на поле, яке описане в тому ж модулі, — це ок, бо ORM реєструє
моделі до читання `data`. Але якщо view посилається на *групу доступу*, цю
групу треба оголосити **вище** в списку.

### Правило нумерації версій

`18.0.1.0.0` розшифровується як:

* `18.0` — версія Odoo (обов'язково, інакше Odoo відмовиться ставити модуль);
* `1` — major твоєї версії модуля (змінюється при зміні моделей даних);
* `0` — minor (нові функції);
* `0` — patch (виправлення).

Odoo порівнює версії, щоб розуміти, чи треба оновлювати модуль при `-u`.

## 3. Як Odoo знаходить модулі: `addons_path`

Odoo шукає модулі у директоріях зі списку `addons_path` у `odoo.conf`.
У нас там три шляхи:

```
.../vendor/odoo/addons          ← стандартні бізнес-модулі (sale, stock, account)
.../vendor/odoo/odoo/addons     ← технічні модулі ядра (base, web, mail)
.../custom_addons               ← НАШІ модулі
```

**Якщо два модулі мають однакову технічну назву, перемагає той, чия директорія
лівіша у списку.** Це не академічна деталь: саме так роблять «модулі-заглушки»,
які повністю перекривають стандартний модуль.

> **Практичне правило:** ніколи не називай свій модуль так само, як
> стандартний Odoo. Якщо треба змінити поведінку `sale` — створи
> `techdistrib_sale` із `depends: ['sale']`. Ніколи не прав `vendor/odoo/`.

## 4. Життєвий цикл запиту (що відбувається, коли ти тиснеш кнопку)

Розглянемо натискання кнопки «Підтвердити» в замовленні:

```
1. Браузер → POST /web/dataset/call_kw
      { model: 'sale.order', method: 'action_confirm', args: [[42]] }

2. Werkzeug приймає запит, Odoo визначає, що це виклик методу моделі.

3. Odoo перевіряє права доступу:
      * чи користувач має групу, яка дозволяє запис у sale.order?
      * чи не забороняє якесь record rule саме цей запис?

4. Створюється `env` — «середовище»: (користувач, курсор, кеш, контекст).

5. ORM завантажує запис id=42 → викликає метод action_confirm().

6. Метод виконує логіку: перевірки, зміна станів, створення пов'язаних
   записів (напр., stock.picking для відвантаження).

7. Якщо все ок — COMMIT транзакції. Якщо виняток — ROLLBACK і traceback.

8. Браузер отримує JSON і перемальовує форму.
```

**Висновок, який з цього випливає:** кожен публічний метод моделі — це
потенційний HTTP-ендпоінт. Тому в Odoo існує конвенція:

* методи, які викликаються з UI, починаються з `action_` і повертають
  **словник-дію** (що показати далі);
* методи з підкресленням (`_compute_...`, `_check_...`) — внутрішні,
  їх UI не викликає.

## 5. Словник термінів, без яких не читається документація

| Термін | Що означає |
|--------|-----------|
| **Model** | Python-клас — опис сутності (`res.partner`, `sale.order`) |
| **Record** | Один рядок у таблиці = один об'єкт у Python |
| **Recordset** | Набір записів — те, що повертає `search()`. Поводиться як список, але методи застосовуються до ВСІХ записів одразу |
| **env** | «Середовище»: `env['res.partner']` дає доступ до моделі; знає поточного користувача, права, кеш |
| **Field** | Колонка в таблиці + Python-атрибут (`Char`, `Float`, `Many2one`...) |
| **View** | XML-опис форми/списку/канбану для конкретної моделі |
| **Action** | «Що зробити при кліку» — відкрити список, форму, звіт, URL |
| **Menu** | Пункт меню; завжди вказує на Action |
| **XML ID** | Унікальний ідентифікатор запису, створеного з XML: `techdistrib_base.field_res_partner__dealer_tier` |
| **Module** | Директорія з `__manifest__.py` |
| **Registry** | Глобальний реєстр усіх моделей і полів, будується один раз при старті |

### Recordset — найважливіша концепція

Новачки пишуть цикли там, де вони не потрібні:

```python
# ❌ Так пишуть ті, хто звик до Django/SQL
for partner in partners:
    if partner.credit_limit > 100000:
        print(partner.name)

# ✅ Так пишуть в Odoo
big = partners.filtered(lambda p: p.credit_limit > 100000)
print(big.mapped('name'))
```

`filtered`, `mapped`, `sorted` — це методи recordset'а, які працюють на
стороні ORM і виконують **один SQL-запит** на весь набір.

## 6. Робочий цикл розробника

Це найпрактичніша частина документа. Запам'ятай цей цикл — ти будеш
повторювати його сотні разів.

```
   ┌─────────────────────────────────────────────────┐
   │ 1. Пишеш/змінюєш код у custom_addons/           │
   └────────────────────┬────────────────────────────┘
                        ▼
   ┌─────────────────────────────────────────────────┐
   │ 2. Оновлюєш модуль:                             │
   │    ./scripts/run_odoo.sh -u techdistrib_base    │
   │    (або кнопка Upgrade у Apps)                  │
   └────────────────────┬────────────────────────────┘
                        ▼
   ┌─────────────────────────────────────────────────┐
   │ 3. Перевіряєш результат у браузері (F5)         │
   └────────────────────┬────────────────────────────┘
                        ▼
   ┌─────────────────────────────────────────────────┐
   │ 4. Помилка? Дивишся traceback → правки → п.2    │
   └─────────────────────────────────────────────────┘
```

### Коли треба оновлювати модуль, а коли — ні

Це питання збиває з пантелику всіх початківців. Правило:

| Що ти змінив | Чи потрібен `-u`? |
|--------------|-------------------|
| Python-код методу (логіку) | ❌ Ні, якщо ввімкнено `dev=reload` — сервер сам перезавантажиться |
| Додав нове **поле** в модель | ✅ **Так** — ORM має створити колонку в Postgres |
| Змінив XML-view (форму, список) | ❌ Ні, якщо ввімкнено `dev=qweb` |
| Змінив `security/ir.model.access.csv` | ✅ Так |
| Додав новий файл у `data` манифесту | ✅ Так |
| Додав нову модель | ✅ **Так** — треба створити таблицю |

> У нас у `config/odoo.conf` увімкнено `dev = reload,qweb,werkzeug,xml,assets`.
> Це означає: зміни в Python і XML підхоплюються **без перезапуску**. Але
> структурні зміни (поля, моделі, права) все одно вимагають `-u`.

### Режим розробника в UI

Увімкни його: **Налаштування → Активувати режим розробника**
(або додай `?debug=1` до URL).

Що він дає:

* меню **Technical** — побачиш «нутрощі»: усі моделі, поля, views, actions;
* на формі з'явиться 🐞-іконка — можна подивитись **View Metadata** і
  побачити, які XML-файли формують цю форму. Це найшвидший спосіб знайти,
  де перевизначити стандартну поведінку;
* у списку полів моделі видно `Field Name` — його треба використовувати в `xpath`.

## 7. Головні «місця сили» для кастомізації

Коли треба змінити стандартну поведінку, є чотири способи, від найлегшого:

| Спосіб | Коли застосовувати | Приклад |
|--------|-------------------|---------|
| **Налаштування** | 80 % випадків! Завжди спершу шукай його | Розклад платежів, одиниці виміру |
| **Наслідування view** | Треба додати поле в стандартну форму | `xpath` у `views/*.xml` |
| **Наслідування моделі** | Треба додати поле/логіку в стандартну модель | `_inherit = 'res.partner'` |
| **Заміна методу** | Треба змінити поведінку | `def action_confirm(self)` |

> **Золоте правило Odoo-розробника:** перш ніж писати код — спитай себе
> «а може, це вже є в налаштуваннях?». Більшість поганих кастомізацій
> народились там, де хтось не дочитав до кінця форму налаштувань.
