# AGENTS.md — інструкції для AI-агентів у odoo-techdistrib

Навчальний проєкт з **Odoo 18 (Community)**: ERP для B2B-дистриб'ютора обладнання.
Код пишеться лише в `custom_addons/`; `vendor/odoo/` — чуже ядро, його тільки читають.

Поглиблені скіли (усі в `.agents/skills/`):

| Скіл | Коли відкривати |
|---|---|
| `odoo-architecture` | куди покласти логіку, коли виносити в `policy/`, скільки DDD має сенс |
| `odoo-module-standards` | створення/правка модуля, маніфест, моделі, безпека, лінтери |
| `odoo-testing` | тести, теги, ACL-тести, пастки тестового режиму |
| `odoo-mcp` | живі запити до бази через MCP, перевірка полів і доменів |

## 1. Середовище

| Компонент | Значення |
|---|---|
| Odoo | 18.0, клон у `vendor/odoo` (тільки читання) |
| Python | 3.12, venv у `.venv/` |
| PostgreSQL | 16 у Docker, `127.0.0.1:5437`, користувач/пароль `odoo`/`odoo` |
| База | `techdistrib`; веб-інтерфейс http://localhost:8069, логін `admin`/`admin` |

```bash
docker compose up -d                     # підняти базу
./scripts/run_odoo.sh                    # запустити Odoo
./scripts/odoo_shell.sh -d techdistrib   # інтерактивна консоль ORM
./scripts/odoo_shell.sh -u <module> -d techdistrib   # оновити модуль після правки коду
./scripts/run_tests.sh <module>          # тести модуля
./scripts/lint.sh                        # ruff + pylint_odoo
```

> `uv` у цьому середовищі може впасти з `Permission denied` на своєму кеші — тоді
> працюй напряму через `.venv/bin/python`.

## 2. Модулі та напрямок залежностей

```
techdistrib_base            дилерська програма на res.partner (рівні, коди, статуси)
   ├── techdistrib_pricing  матриця знижок → product.pricelist
   ├── techdistrib_credit   кредитні ліміти, блокування, погодження
   ├── techdistrib_warranty RMA за серійним номером
   └── techdistrib_reports  QWeb-звіти, cron
```

Залежність завжди **в один бік, без циклів**. Спільне піднімається в `base`,
а не імпортується сусідом.

## 3. Головний принцип проєкту

> **Спершу перевір, чи це вже є в Odoo.** Найкраща кастомізація — конфігурація
> стандартного механізму, а не переписування.

Це не гасло, а те, на чому стоять два модулі з чотирьох:

- `techdistrib_pricing` не рахує ціни сам — він перетворює матрицю знижок на
  штатні `product.pricelist.item`.
- `techdistrib_credit` не вигадує ліміти — переюзує `res.partner.credit_limit`,
  `credit`, `credit_to_invoice` і **розширює** (`_inherit`) наявний
  `partner_credit_warning`, а не замінює його.

Перед новою моделлю перевір `list_models` через MCP або `grep` по `vendor/odoo`.

## 4. Обов'язкові правила

1. **Не редагувати `vendor/odoo/`.** Розширення — тільки через `_inherit`.
2. **Перевизначення методів ядра — завжди з `super()`** і з коментарем, ЩО і НАВІЩО змінено.
3. **Кожна нова модель → рядок у `security/ir.model.access.csv`.** Модель без ACL
   і модель із правами «всім» — обидві помилки.
4. **Порядок `data` у маніфесті** строго: security → data → views → menus.
   Меню завжди останні.
5. **Переклад у методах — `self.env._()`**, не модульний `_()` (Odoo 18; для cron
   і листів різниця реальна).
6. **Не запускати `ruff` без `ruff.toml` проєкту.** Сирий `ruff --fix` видаляє
   `from . import models` (тиха поломка реєстрації моделей) і переписує
   `_('...%s...')` у f-strings (ламає переклади). Деталі — в `odoo-module-standards`.
7. **Незбережене поле не можна шукати в домені.** Перед доменом перевіряй
   `store`/`searchable` (через MCP або по коду). Це головна пастка ORM.
8. **Не робити запит у циклі.** Для кожного запису `search` — це N+1; використовуй
   `mapped` / `filtered` / `read_group`.
9. **Секрети — лише в `.env`** (git-ignored). Не комть паролі баз і ключі.
10. **Після змін — тести й лінтер зелені.** Див. §6.

## 5. Куди писати код

| Що | Куди |
|---|---|
| Поля, computed, constraints, оркестрація | `models/` |
| **Чиста логіка без `self.env` і без БД** (розрахунки, політики, рішення) | `policy/` — і туди ж безбазовий тест |
| Багатокрокові дії в UI | `wizards/` (`TransientModel`) |
| Доступ до зовнішніх систем | вузький адаптер, щоб підмінявся в тестах |

Правило винесення в `policy/`: логіка **не читає `env`**, повертає **значення**,
і ти хочеш тестувати її **без бази**. Не виконується хоч одна умова — лишай на
моделі. Це не компроміс, а правильне місце для такого коду в Odoo.

**Не роби** репозиторіїв над `self.env['x'].search()`: це втрачає правила
записів (`ir.rule`), права й prefetch. Розгорнуто — в `odoo-architecture`.

## 6. Definition of Done

```bash
./scripts/run_tests.sh <module>
./scripts/lint.sh <module>     # baseline: 9.96/10, див. odoo-module-standards §5
```

Плюс: модель має ACL; новий файл у `data` існує; бізнес-правило покрите тестом,
який падає без зміни. **Якщо додав модель — додай і тест на доступ**: тести
біжать під superuser і ACL не перевіряють (див. `odoo-testing` §7).

## 7. Документація проєкту

`docs/00-overview.md` … `docs/04-module-credit.md` — навчальні матеріали,
читаються по порядку. Це **не** довідник API: джерело правди про поведінку —
код, про живу базу — MCP. Де документи розходяться з кодом, правий код.

Стиль коментарів у проєкті — **пояснювати «чому», а не «що»**: розгорнуті
українські коментарі над нетривіальними рішеннями. Тримайся його: коментар
на кшталт `# збільшуємо лічильник` не додає нічого, а `# ondelete='restrict':
не можна видалити номер, якщо по ньому є звернення` — додає.
