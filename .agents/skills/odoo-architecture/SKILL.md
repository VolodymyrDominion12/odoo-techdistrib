# Архітектура в Odoo: де межа, за якою шарінг починає шкодити

**Джерело правди — код.** Усі твердження про API нижче перевірені по
`vendor/odoo/` (гілка 18.0, commit `840e84e9`), а не взяті зі статей. Якщо
сумніваєшся — перевіряй так само: `grep -rn "<назва>" vendor/odoo/odoo/`.

## 1. Головна теза

**Odoo — це вже архітектура, і вона навмисно «товста».** Це Active Record ORM,
де клас моделі одночасно є:

| Роль у Clean Architecture | Що грає цю роль в Odoo |
|---|---|
| Сутність домену | клас `models.Model` |
| Репозиторій | `self.env['model'].search()` / `browse()` |
| Unit of Work | `self.env.cr` + транзакція запиту |
| DI-контейнер | `self.env` (registry) |
| Шар безпеки | `ir.model.access` + `ir.rule`, застосовані **всередині ORM** |
| Механізм розширення | `_inherit` (навмисний monkey-patching) |
| DTO / колекція | сам recordset (`mapped`, `filtered`, `sorted`) |

Тому **переносити Clean Architecture на Odoo 1:1 не можна** — і це не питання
смаку. Нижче 5 конкретних причин, кожна з яких є помилкою, а не стилем.

### Чому саме не можна

1. **Репозиторій над ORM знищує безпеку.** `self.env['x'].search()` всередині
   застосовує `ir.rule` (правила записів) і ACL. Сховавши доступ за своїм
   репозиторієм, ти або дублюєш цю логіку гірше за ядро, або виконуєш SQL
   напряму — і тоді мультикомпанія та правила записів **тихо перестають
   працювати**. Це вже не архітектурна дискусія, а діра в доступі.
2. **Recordset — це не «список записів», а колекція з кешем.** `search()`
   повертає ліниву колекцію з prefetch: один запит на все поле для всіх
   записів. Перекладаючи її в `list[dict]` на межі шару, ти втрачаєш
   prefetch і отримуєш N+1, якого в Odoo не було.
3. **`_inherit` ламається, якщо логіка живе поза моделлю.** Інший модуль
   розширює ТВОЮ модель: перевизначає метод, додає поле, міняє `@api.depends`.
   Якщо бізнес-логіка переїхала в паралельний «доменний» клас, цей механізм
   розширення до неї не дістає — і модуль втрачає головну перевагу Odoo.
4. **Транзакцію тримає фреймворк.** `env.cr` відкривається й закривається
   рушієм; `savepoint`-и для вкладених збоїв робить ORM. Власний Unit of Work
   це просто друга реалізація того, що вже гарантовано.
5. **Ідентичність запису вже є.** У запису є `id` у БД і місце в кеші ORM.
   Окремий «агрегат» із власною ідентичністю вимагає мапінгу в обидва боки —
   і кожна помилка в цьому мапінгу це баг із втраченими змінами.

## 2. Що з цього справді варто взяти (приблизно 20–30 %)

Виносити логіку з моделі треба — але за **правилом рішення**, а не за модою.

### Правило рішення

> Винось у звичайний Python-модуль (`services/`), якщо виконуються **усі три**:
> 1. логіка **не читає й не пише** через `self.env` (це рішення або розрахунок, не доступ до даних);
> 2. результат — **значення або виняток**, а не запис у БД;
> 3. ти хочеш тестувати її **без бази** (мілісекунди замість хвилин) **або** переюзати в кількох моделях.

Не виконується хоч одна умова — **лишай на моделі**. Це не компроміс, це
правильне місце для такого коду в Odoo.

### Що виноситься добре (реальні приклади саме цього проєкту)

| Що | Де зараз | Куди проситься |
|---|---|---|
| Арифметика гарантійних дат (початок + термін місяців → кінець, чи діє на дату) | `techdistrib_warranty` | чиста функція `services/warranty_dates.py` |
| Рішення «чи можна підтвердити замовлення» за сумою, дебіторкою й схваленням | `techdistrib_credit` | чиста політика `services/credit_policy.py` |
| Обчислення відсотка знижки з матриці «рівень × категорія» | `techdistrib_pricing` | чистий резолвер `services/discount_lookup.py` |
| Клієнт зовнішнього API (портал вендора, платіжка, доставка) | — | адаптер із вузьким інтерфейсом, щоб у тестах підмінявся |

**Виграш вимірюваний:** зараз КОЖЕН тест у проєкті — це `TransactionCase`,
тобто повний цикл «підняти тестову базу → встановити модуль → прогнати».
Чиста функція тестується звичайним `unittest`/`pytest` без Odoo взагалі.

### Що НЕ виноситься (це і є карго-культ)

- Репозиторій/шлюз над `self.env['x'].search()` — втрата правил записів і prefetch.
- DTO-мапінг між «шаром даних» і «шаром домену» — recordset уже є і тим, і тим.
- Портовий інтерфейс (hexagonal) навколо ORM — ORM не «деталь, яку можна замінити», на ньому стоїть усе.
- Власний DI-контейнер — `self.env` уже реєстр; сервіс береться як `self.env['x']`.
- «Анемічна» модель: поля в моделі, а вся логіка в сервісах, які смикають її ззовні. В Odoo навпаки — логіка поруч із полями, бо так її бачать і UI, і `_inherit`, і майстер-форми.

## 3. Справжня межа контексту в Odoo — це МОДУЛЬ

DDD-поняття **bounded context** в Odoo реалізується не теками й не шарами, а
**аддонами та графом `depends`**. Архітектура проєкту — це цей граф:

```
techdistrib_base            (res.partner: дилерська програма)
   ├── techdistrib_pricing  (прайс-листи рівнів)
   ├── techdistrib_credit   (кредитні ліміти, погодження)
   ├── techdistrib_warranty (RMA за серійним номером)
   └── techdistrib_reports  (QWeb-звіти, cron)
```

Практичні наслідки, яких треба дотримуватись:

- **Залежність завжди в один бік, без циклів.** `pricing` не має знати про `credit`.
  Спільне піднімається в `base`, а не імпортується сусідом.
- **Модуль не чіпає `vendor/odoo/`** — тільки `_inherit`. Це головне правило проєкту.
- **Нова бізнес-сутність = новий модуль**, якщо в неї свій життєвий цикл і свої
  права доступу. Якщо це лише поля на існуючій моделі — розширення в наявному модулі.
- Перед тим як писати — **перевір, чи цього немає в ядрі**. У проєкті це вже
  зроблено зразково: `pricing` не переписує ціноутворення, а конфігурує
  `product.pricelist`; `credit` розширює `partner_credit_warning`, а не замінює.

## 4. Куди що кладеться в модулі

```
custom_addons/<module>/
├── __manifest__.py         # дані, не код
├── __init__.py             # from . import models  (+ services, wizards)
├── models/                 # ORM: поля, constraints, computed, оркестрація
├── services/               # ← НОВЕ: чиста логіка. Без env, без БД, без записів
├── wizards/                # TransientModel (багатокрокові дії в UI)
├── views/                  # XML: форми, списки, меню
├── data/                   # XML: послідовності, cron, довідники
├── security/               # групи (XML) + ir.model.access.csv
├── report/                 # QWeb
├── static/                 # assets (у маніфесті — ключ `assets`)
└── tests/                  # TransactionCase + чисті тести для services/
```

**Контракт шару `services/`** (це і є вся «чиста архітектура», яку тут варто мати):

- **Можна** імпортувати: стандартну бібліотеку, `decimal`, `datetime`, `dateutil`.
- **Можна** `from odoo.tools.translate import _` — якщо функція формує текст для користувача.
- **Не можна**: `self.env`, `models.Model`, `search`/`create`/`write`, читання `.env`, мережу.
- Приймає **значення** (Decimal, date, str), повертає **значення** або кидає
  `ValueError`/доменний виняток. Ніколи не кидає `UserError` — це UI-рівень.
- Модель кличе сервіс, а `UserError` з людським текстом формує вже модель.

## 5. Підводні камені, перевірені по `vendor/odoo/`

Це те, на чому агенти найчастіше помиляються, бо інформація зі старих версій
або з майбутніх:

| Твердження | Правда для 18.0 |
|---|---|
| `models.Constraint` для SQL-обмежень | **НЕ існує** в 18.0 (`grep -rn "class Constraint" vendor/odoo/odoo/models.py` — порожньо). Використовуй `_sql_constraints` |
| `SavepointCase` | **Видалено.** Є `BaseCase`, `TransactionCase`, `SingleTransactionCase`, `HttpCase` (`vendor/odoo/odoo/tests/common.py`) |
| `_('...')` модульний | Працює, але в 18.0 є `self.env._()` (`vendor/odoo/odoo/api.py:788`), який перекладає **з урахуванням мови середовища**. Для cron і листів це те, що треба |
| `fields.Command` | Є (`vendor/odoo/odoo/fields.py:4294`). Старі триплети `(0, 0, {...})` ще працюють, але новий код — на `Command` |
| `qweb` у маніфесті | Для assets ключ — `assets` |

## 6. Антипатерни, які ламають саме цей проєкт

1. **Переписати те, що є в ядрі.** У проєкті два модулі тримаються на зворотному
   принципі («конфігуруй стандартний механізм»). Порушення цього — головна
   архітектурна помилка тут, важливіша за будь-який шарінг.
2. **Циклічна залежність модулів.** `depends` — це DAG. Цикл = неможливість
   встановити модуль поодинці.
3. **Логіка у views/wizard, що дублює модель.** Правило змінюється в двох місцях і розходиться.
4. **`sudo()` для обходу прав.** Легітимний лише в cron/системних діях, де
   користувача справді немає. У дії користувача — це приховування проблеми з правами.
5. **Прямий SQL замість ORM.** Обходить правила записів і кеш. Припустимо лише
   для звітів/аналітики з усвідомленням ціни й ніколи — для запису.

## 7. Короткий підсумок для швидкого рішення

```
Треба додати логіку?
│
├── Це доступ до даних (search/browse/create/write)? ──────► модель, через ORM
├── Це перевірка цілісності одного запису? ────────────────► @api.constrains
├── Це похідне значення з інших полів? ────────────────────► computed + @api.depends
├── Це реакція на зміну в UI (підказка)? ──────────────────► @api.onchange
├── Це заборона дії, що залежить від РІЗНИХ моделей? ──────► модель (метод дії),
│                                                            бо потрібен контекст і права
└── Це чистий розрахунок/рішення без БД і без env? ────────► services/, і туди ж
                                                             БЕЗБАЗОВИЙ тест
```

Деталі синтаксису й конвенцій модуля — у скілі `odoo-module-standards`;
про тести — у `odoo-testing`.
