# Конвенції модулів Odoo 18 (проєкт odoo-techdistrib)

Версія: **Odoo 18.0** (`vendor/odoo`, гілка 18.0). Python **3.12**, venv у `.venv/`.
Усі факти про API перевірені по `vendor/odoo/`, а не взяті зі статей.

## 1. Маніфест `__manifest__.py`

Це **дані, а не код**: жодних імпортів і обчислень — файл читається при кожному
старті сервера.

```python
{
    'name': 'TechDistrib — <Назва>',
    'version': '18.0.1.0.0',          # MAJOR.<odoo>.<major>.<minor>.<patch>
    'category': 'Sales/Sales',
    'summary': '<один рядок для списку модулів>',
    'description': """...""",          # reST, без відступів і спецсимволів
    'depends': ['techdistrib_base', 'sale_management', 'mail'],
    'data': [ ... ],                   # порядок СТРОГО як у §2
    'installable': True,
    'application': False,              # True лише для кореневого модуля програми
    'license': 'LGPL-3',
}
```

Правила, яких тримається весь проєкт:

- `depends` — **змістовний список**. Кожна залежність має бути обґрунтована
  коментарем: навіщо саме вона (див. `techdistrib_credit` — там це зроблено зразково).
- `application: True` — тільки в `techdistrib_base`. Решта розширюють існуючі застосунки.
- `version` — завжди `18.0.x.y.z`. Перевіряється лінтером (`manifest-version-format`).
- `license` — `LGPL-3`, як у ядра.

## 2. Порядок `data` — не косметика, а вимога

Odoo читає файли **строго зверху вниз**, і кожен наступний може посилатися лише
на створене попереднім:

```python
'data': [
    # 1. Безпека: спершу групи (XML), бо CSV посилається на них
    'security/<module>_security.xml',
    'security/ir.model.access.csv',
    # 2. Дані: послідовності, довідники, cron
    'data/ir_sequence_data.xml',
    'data/<довідник>_data.xml',
    'data/ir_cron_data.xml',
    # 3. Подання — посилаються на дані
    'views/<model>_views.xml',
    'views/<inherit>_views.xml',
    # 4. Меню — посилаються на actions із views, тому ЗАВЖДИ останні
    'views/menus.xml',
],
```

**Перевірка перед комітом:** кожен файл зі списку існує. Помилка тут — це
`F8101 resource-not-exist` від pylint_odoo і модуль, який не встановиться.

## 3. Моделі

- `_name` — `techdistrib.<сутність>` (крапки, нижній регістр); `_description` — обов'язково.
- `_inherit = ['mail.thread', 'mail.activity.mixin']` — для сутностей із життєвим циклом,
  які коментують (`tracking=True` на ключових полях).
- `_order` — явний, якщо порядок має значення для користувача.
- **Імпорт**: `from odoo import _, api, fields, models` — саме такий порядок
  (алфавітний, як вимагає OCA і `ruff` правило `I001`).
- Переклад усередині методів: **`self.env._()`**, а не модульний `_()`
  (`vendor/odoo/odoo/api.py:788`). Різниця реальна для cron і листів: `env._`
  бере мову середовища.
- `@api.model_create_multi` замість `create`, якщо перевизначаєш створення.
- `x2many` у `create`/`write` — через `fields.Command` (`fields.py:4294`),
  не через триплети `(0, 0, {...})` у новому коді.
- **`@api.depends` при перевизначенні ЗЛИВАЮТЬСЯ** з батьківськими
  (`fields.py::get_depends` → `resolve_mro`). Повторювати їх не потрібно, але
  писати корисно для читача — так робить `techdistrib_credit`.
- SQL-обмеження — `_sql_constraints`. **`models.Constraint` у 18.0 НЕ існує**
  (`grep -rn "class Constraint" vendor/odoo/odoo/models.py` — порожньо).
- Перевизначення методів ядра — **завжди з `super()`** і з поясненням, ЩО саме
  і НАВІЩО змінюється.

## 4. Безпека: три шари, усі обов'язкові

1. **Групи** — `security/<module>_security.xml` через `record` на `res.groups`
   (+ категорія, щоб групи не змішувались зі стандартними).
2. **ACL** — `security/ir.model.access.csv` для **кожної нової моделі**.
   Формат: `id,name,model_id:id,group_id:id,perm_read,perm_write,perm_create,perm_unlink`.
   Нова модель без рядка в ACL — помилка; нова модель із правами всім підряд — теж.
3. **Правила записів** — `ir.rule` з `domain_force` для обмеження по компанії/менеджеру.

`sudo()` — лише для системних дій без користувача (cron, міграції). У дії
користувача він означає, що права налаштовані неправильно; приховувати це
`sudo()` заборонено. Мультикомпанія: враховуй `self.env.company`, а не
`self.env.user.company_id` навмання.

## 5. Лінтери: `./scripts/lint.sh`

Одна команда на все:

```bash
./scripts/lint.sh                          # усі модулі
./scripts/lint.sh techdistrib_credit       # один модуль
./scripts/lint.sh --fix                    # автоправки ruff (безпечні, див. нижче)
```

Скрипт сам створює `.venv-lint` (ruff + pylint_odoo), тримає кеш pylint у
проєкті (`.pylint-cache/`, щоб не залежати від `~/.cache`) і запускає
`pylint` у послідовному режимі.

### 🔴 НЕБЕЗПЕЧНІ АВТОПРАВКИ — прочитай перед `--fix`

Сирий `ruff` (без `ruff.toml` з проєкту) на Odoo-аддоні робить дві руйнівні речі:

| Правило | Що зробить | Наслідок |
|---|---|---|
| `F401` | видалить `from . import models` з `__init__.py` | **модуль встановиться без жодної моделі й без помилки** — тиха поломка |
| `UP031` | перепише `_('...%s...')` у f-string | f-string обчислюється ДО `_()`, тому в `.po` потрапляє готова строка — переклад стає неможливим |

Обидва правила **вимкнені** в `ruff.toml` з поясненням. Те саме зроблено для
`RUF001/002/003`: вони шукають «неоднозначні» символи Unicode, і на цьому
проєкті (коментарі українською) давали **1549 із 1570** початкових зауважень,
ховаючи справжні знахідки.

**Висновок, який треба засвоїти:** не запускай лінтер без конфіга проєкту і не
«виправляй» те, що лінтер позначив, не переконавшись, що це не хибне
спрацьовування в контексті Odoo. Приклад із цього ж проєкту: `missing-return` на
`_compute_partner_credit_warning` **виглядає** як баг, а насправді метод
виставляє поле через `self.field = ...` і `super()` там не має нічого повертати.

### Поточний baseline (виміряно, не оцінено)

На момент написання `./scripts/lint.sh` дає **9.96/10** і 7 реальних зауважень
pylint (решта — 19 автоправних `I001` порядку імпортів і один `E501`):

| Файл | Що | Що робити |
|---|---|---|
| `techdistrib_base/models/res_partner.py:391` | `W8120` позиційні `%s` у `_()` з двома аргументами | перевести на `%(name)s` — інакше перекладач не зможе змінити порядок |
| `techdistrib_base/models/res_partner.py:483` | `W8163` `search([])` без `limit` | додати `limit` або аргументувати, чому довідник малий |
| `techdistrib_base/models/res_partner.py:489` | `W0640` + `B023` — лямбда захоплює змінну циклу | зв'язати явно: `lambda t, seq=current.sequence: ...` |
| `test_warranty.py:321,344` | `W0612` невикористаний `picking` | `_picking` або прибрати |
| `sale_order.py:117` | `C0301` рядок 103 символи | перенести |

`W8161 prefer-env-translation` (63 місця) **вимкнено свідомо** в `.pylintrc` як
задокументований борг: це окремий механічний коміт із прогоном тестів, а не
супутній ефект іншої задачі. Рецепт міграції — у коментарі до `.pylintrc`.

**Правило роботи з лінтером:** зауваження або виправляється, або правило
вимикається **з коментарем, чому саме**. Мовчазне вимкнення заборонене:
наступний агент не знатиме, що це було рішення, і «полагодить» його назад.

## 6. Видалене й застаріле в 18.0 — щоб не тягнути чужі поради

Агенти часто приносять код зі статей під 16/17. У 18.0 ці API **вже не працюють**:

| Замість цього | У 18.0 |
|---|---|
| `name_get()` | **видалено** → `_compute_display_name` |
| оператор домену `inselect` / `not inselect` | **видалено** з `TERM_OPERATORS` |
| `invalidate_cache()` | **не існує** → `invalidate_model()` / `invalidate_recordset()` |
| `check_access_rights()` / `check_access_rule()` | **застарілі** → `check_access()` / `has_access()` / `_filtered_access()` |
| `models.Constraint` для SQL-обмежень | **не існує в жодній гілці** → `_sql_constraints` |
| `SavepointCase` | **видалено** → `TransactionCase` (він і є savepoint-варіант) |
| `type='jsonrpc'` у контролерах | це 19.0; у 18.0 — `type='json'` |

Ваш код, до речі, чистий: жодного з цих API в `custom_addons/` немає.

Перед сирим SQL — `self.env.flush_all()` (або `flush_model`), інакше читаєш
застарілі рядки. І пам'ятай: **сирий SQL обходить правила записів** — навіть
параметризований варіант ядро називає «no injection, but still wrong».

### Пастки, які легко не помітити

- **`compute_sudo` за замовчуванням дорівнює `store`.** Тобто *збережене*
  computed-поле обчислюється **від імені superuser** і бачить більше даних, ніж
  користувач. Якщо результат має поважати права — став `compute_sudo=False` явно.
  `related`-поля теж `sudo` за замовчуванням.
- **`readonly` computed-поля дорівнює `not inverse`**: додав `inverse` — поле
  автоматично стало редагованим.
- **`@api.onchange` НЕ виконується ні при `create`/`write`, ні при імпорті.**
  Бізнес-інваріанти — у `create`/`write`/`@api.constrains`; `onchange` лише UI.
- **Cron не має автовиявлення.** Метод `_cron_*` сам по собі нічого не запускає —
  потрібен запис `ir.cron` у `data/ir_cron_data.xml` (як у `techdistrib_warranty`).
  У 17+ `ir.cron` делегує до `ir.actions.server`, тому `code`, `model_id`, `state`
  живуть там.
- **Порожній `group_id` в ACL означає доступ ДЛЯ ВСІХ** (включно з portal і
  public), а не «ні для кого». Модель **взагалі без ACL** доступна лише
  superuser. Wizard-и (`TransientModel`) теж потребують рядка в ACL.
- **`sudo()` обходить перевірки ПРАВ, але не ЦІЛІСНОСТІ**: `@api.constrains`,
  SQL-обмеження й `_check_company` продовжують діяти. Тому `sudo()` не можна
  використовувати, щоб «зробити так, щоб AccessError зник» — це завжди лікується
  ACL, правилом або `with_user()`.
- **`fields.Char(groups=...)` сильніший, ніж здається**: він ріже не лише
  `read`/`write`, а й домени пошуку, `order=` і `_read_group`. Але `sudo()`
  обходить і його. Плюс це **окремий** механізм від `groups=` на вузлі в'ю.
- **Мультикомпанія:** `_check_company_auto = True` нічого не робить, доки не
  виставлений; `default=lambda self: self.env.company` (не
  `self.env.user.company_id` — той ігнорує перемикач компаній); у `domain_force`
  для компаній ядро використовує `parent_of`, а не `in` — інакше ламається
  видимість материнської компанії.
- **`Command` — Python-ідіома, але триплети НЕ видалені**: на RPC-дроті
  `(0, 0, {...})` досі обов'язковий (це прямо в docstring `Command`). У Python і
  в XML `eval` використовуй `Command.*`.
- **Посилання на computed як на строку**: `compute="_compute_x"`, а не лямбда чи
  пряме посилання на функцію — інакше підклас не зможе його перевизначити.

## 7. Чого не робити

- Не редагувати `vendor/odoo/` — це чужий код; усе через `_inherit`.
- Не комітити `.env`, філстор, логи, `__pycache__`.
- Не дублювати те, що є в ядрі (головний принцип проєкту: **конфігуруй
  стандартний механізм, а не переписуй його**).
- Не писати запит у циклі: `search` для кожного запису — це N+1; використовуй
  `mapped`/`filtered`/`read_group`.
- Не чіпати `create`/`write` без `super()`.
- Не використовувати `fields.Command` там, де достатньо прямого присвоєння.

Структурні рішення (куди покласти логіку, коли виносити в `policy/`) — у скілі
`odoo-architecture`. Тести — у `odoo-testing`.
