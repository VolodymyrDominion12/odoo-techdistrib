# Odoo MCP: жива база як джерело фактів

MCP-сервер `fast-odoo-mcp` підключається до робочої бази `techdistrib` через
штатний XML-RPC Odoo 18 — **без встановлення модулів у Odoo**. Агент отримує
тули, які читають реальні моделі, поля й записи.

Файли конфігурації (обидва вже в проєкті):

| Файл | Хто читає |
|---|---|
| `.cursor/mcp.json` | Cursor |
| `.agents/mcp_config.json` | Antigravity (workspace-local) |
| `~/.dsh/profiles/web/cordis.patch.yml` | DSH (рядок `mcp-odoo`) |

Середовище сервера — `.venv-mcp/` у корені проєкту (в `.gitignore`). Якщо його
немає: `python3 -m venv .venv-mcp && .venv-mcp/bin/pip install fast-odoo-mcp`.

## 1. Що вміє сервер

| Тул | Навіщо |
|---|---|
| `get_model_fields` | **головний інструмент**: усі поля моделі з `type`, `store`, `searchable`, `string`, `depends`, `help`, `selection` |
| `list_models` | знайти модель за назвою (у т.ч. перевірити, чи є вона в ядрі) |
| `search_records` | реальні записи за доменом — можна побачити справжні дані |
| `get_record` | один запис за id |
| `validate_domain` | перевірити синтаксис домену й одразу побачити `count` |
| `get_model_methods` | які методи є на моделі (корисно, щоб знайти точку розширення) |
| `simulate_onchange` | побачити, що зміниться в UI при зміні поля, не відкриваючи UI |
| `server_info` / `get_public_config` | стан з'єднання, БД, режим read-only |

## 2. Три рецепти, які реально економлять час

### Рецепт 1: перевірити, чи поле можна шукати в домені

**Це найцінніше.** Ваша ж документація (`docs/02`, «🔴 ГОЛОВНА ПАСТКА: незбережені
поля не можна шукати») описує цю помилку — а MCP дає перевірити її заздалегідь:

```
get_model_fields(model="res.partner", search="dealer")
```

У відповіді дивись на два прапорці:

| Поле | `store` | `searchable` | Наслідок |
|---|---|---|---|
| `dealer_status` | `true` | `true` | ✅ можна в `domain` і `@api.depends` |
| `dealer_experience_months` | `false` | `false` | ❌ **не можна** шукати; домен мовчки поведе себе не так |
| `dealer_confirmed_order_count` | `false` | `false` | ❌ те саме |

Правило: **перед тим як писати `search([('поле', ...)])` або `ir.rule` з
`domain_force`, переконайся, що поле `searchable: true`.** Якщо ні — або додай
`store=True`, або перепиши фільтр на полі, яке зберігається.

### Рецепт 2: не дублювати те, що вже є в ядрі

```
list_models(search="credit")        → чи є готова модель
get_model_fields(model="res.partner", search="credit")
```

Головний принцип проєкту — **конфігурувати стандартний механізм, а не
переписувати**. MCP дозволяє перевірити це до написання коду: `res.partner` уже
має `credit_limit`, `credit`, `credit_to_invoice` — тому `techdistrib_credit` їх
переюзує, а не заводить свої.

### Рецепт 3: узяти реальні дані для тесту

```
search_records(model="res.partner", domain=[["is_dealer","=",true]],
               fields=["name","dealer_code","dealer_tier_id"], limit=5)
```

У проєкті реально є 5 дилерів (`DLR-00001` «ТОВ Альфа-Тех» Gold тощо). Але
**не хардкодь ці дані в тести**: тестова база створюється порожньою з
`--without-demo=all`, тож тест має створювати свої записи в `setUpClass`.
MCP тут — щоб зрозуміти **форму** даних, а не щоб узяти конкретні рядки.

## 3. 🔴 Пастка, яку я знайшов саме через MCP: кастомні моделі недоступні

Спроба прочитати `techdistrib.warranty.claim` дає:

```
Access denied: Operation 'read' not allowed on model 'techdistrib.warranty.claim'
```

**Це не баг MCP.** Причина в ACL: `security/ir.model.access.csv` модулів
`techdistrib_base`, `techdistrib_credit`, `techdistrib_warranty` дають права
**лише кастомним групам** (`group_dealer_user`, `group_dealer_manager`,
`group_credit_controller`), а користувач `admin`, під яким логіниться MCP,
у цих групах **не перебуває** — і жоден файл безпеки його туди не додає.

Що з цього випливає:

- `res.partner` і стандартні моделі читаються нормально (там ACL широкі) — і
  кастомні поля на них теж видно.
- Власні моделі проєкту (`techdistrib.*`) — ні.

**Три способи виправити** (вибирай свідомо):

1. Додати в `techdistrib_base/security/techdistrib_security.xml`:
   ```xml
   <record id="group_dealer_manager" model="res.groups">
       <field name="users" eval="[(4, ref('base.user_admin'))]"/>
   </record>
   ```
   Найпростіше для навчального проєкту: адміністратор справді має бачити ці дані.
2. Завести окремого користувача в потрібній групі й логінити MCP під ним —
   правильніше для реальної експлуатації.
3. Дати `base.group_user` право `read` у CSV — **не рекомендую**: це відкриє
   кредитні й гарантійні дані всім внутрішнім користувачам.

**І головне:** цей дефект доступу **неможливо зловити тестами** в поточному
вигляді — див. скіл `odoo-testing` §7. MCP тут виявився єдиним інструментом,
який його показав.

## 4. Безпека

- MCP працює в режимі **read-only**: тулів `create/update/delete` у списку
  немає. Узагалі.
- Загальна «шпарина» `execute_method` теж закрита другим списком
  (`ODOO_MCP_SAFE_METHODS`), у якому немає `write`. Перевірено:
  `Access denied: Method 'write' is not in the MCP safe method list.`
- **Облікові дані лежать у конфігах відкритим текстом** (`admin`/`admin`) — як і
  в `README.md`. Для локальної навчальної бази це прийнятно, але якщо база
  колись перестане бути локальною, треба перейти на `ODOO_API_KEY` і прибрати
  конфіг із git.
- `ODOO_LOCALE=en_US` **обов'язковий**: типове значення сервера — `zh_CN`, а в
  базі встановлено лише `en_US`, тому Odoo відповідає
  `Invalid language code: zh_CN` на будь-який запит.

## 5. Коли MCP НЕ треба

MCP показує **стан бази**, а не логіку. Тому:

| Питання | Правильне джерело |
|---|---|
| Що робить метод, як рахується поле | **вихідний код** у `custom_addons/` |
| Які ключі маніфесту, порядок `data` | код + скіл `odoo-module-standards` |
| Як поводиться ядро Odoo | `vendor/odoo/` (він у вас є — це найшвидший довідник) |
| Що реально лежить у полі, який `type`/`store` | **MCP** |
| Чи існує поле в ядрі до того, як я додам своє | **MCP** |
| Чи пройде домен, скільки дасть записів | **MCP** (`validate_domain`) |

**Найважливіше обмеження:** база відображає **встановлену** версію модуля. Після
правки моделі поле в базі не з'явиться, доки модуль не оновлено. Тому не роби
висновок «моє поле не працює» з MCP, поки не виконав:

```bash
./scripts/odoo_shell.sh -u <module> -d techdistrib
```

Інакше MCP показуватиме стару структуру, і це виглядатиме як помилка коду, якою
не є.
