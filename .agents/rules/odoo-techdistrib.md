# odoo-techdistrib — правила розробки

Навчальний ERP на **Odoo 18 (Community)** для B2B-дистриб'ютора. Код — лише в
`custom_addons/`; `vendor/odoo/` — чуже ядро, тільки читання.

> У панелі Rules постав цьому правилу активацію **Always On** (або **Model
> Decision** — опис вище підходить як тригер).

## Головний принцип

**Спершу перевір, чи це вже є в Odoo.** Найкраща кастомізація — конфігурація
стандартного механізму, а не переписування. `techdistrib_pricing` перетворює
матрицю знижок на штатні `product.pricelist.item`, а не рахує ціни сам;
`techdistrib_credit` розширює наявний `partner_credit_warning`, а не замінює його.

Перед новою моделлю — `list_models` через MCP або `grep` по `vendor/odoo/`.

## Обов'язково

1. Не редагувати `vendor/odoo/` — розширення тільки через `_inherit`.
2. Перевизначення методів ядра — завжди з `super()` і з поясненням, що змінено.
3. Кожна нова модель → рядок у `security/ir.model.access.csv` **і тест на доступ**.
   Модель без ACL і модель із правами «всім» — обидві помилки.
4. Порядок `data` у маніфесті: security → data → views → menus (меню останні).
5. Переклад у методах — `self.env._()`, не модульний `_()`.
6. Незбережене поле не можна шукати в домені — перевіряй `store`/`searchable`
   перед тим, як писати `search([...])` або `domain_force`.
7. Не робити `search` у циклі (N+1) — використовуй `mapped`/`filtered`/`read_group`.
8. Секрети — лише в `.env` (git-ignored).

## Лінтери — обережно

```bash
./scripts/lint.sh            # ruff + pylint_odoo з конфігами проєкту
```

**Не запускай `ruff` без `ruff.toml` проєкту.** Сирий `ruff --fix` на Odoo-аддоні:
- видаляє `from . import models` з `__init__.py` (правило F401) → модуль
  встановиться **без моделей і без помилки**;
- переписує `_('...%s...')` у f-strings (UP031) → ламає переклади;
- дає ~1549 зауважень `RUF001-003` на кирилицю в коментарях, ховаючи справжні.

Зауваження або виправляється, або правило вимикається **з коментарем, чому саме**.
Мовчазне вимкнення заборонене: наступний агент «полагодить» його назад.

## Тести

Тести біжать під **superuser (uid 1)**, який обходить усі ACL і правила записів.
Тому зелений прогін **не означає**, що реальний користувач щось побачить. Кожна
нова модель потребує окремого тесту доступу через `new_test_user` +
`with_user` — див. скіл `odoo-testing` §7.

```bash
./scripts/run_tests.sh <module>                        # тести
./scripts/odoo_shell.sh -u <module> -d techdistrib     # оновити модуль після правки
```

## Жива база (MCP)

Підключено MCP-сервер Odoo (read-only, база `techdistrib`). Використовуй його,
щоб дізнатись **факти про дані**: які поля реально є, `store`/`searchable`,
скільки записів дасть домен (`validate_domain`), чи є модель у ядрі.

Пам'ятай: MCP показує **встановлену** версію модуля. Після правки моделі поле
з'явиться лише після `-u <module>` — не роби висновок «код не працює» раніше.

Логіку (що робить метод) читай у коді, а не в MCP.
